## Narrowing the feature set

Anchor: 1490 · U5 · L20 · 00:00–00:40

Unfortunately, we will not be able to use every idea that comes out of research in our project. We will use two tools for this: the MoSCoW method and the Functionality Matrix (*matriz de funcionalidad*). They will help us prioritize functionalities and define what our minimum viable product (*producto mínimo viable*) needs to have.

First, we need to lay out all the functionalities that have come out of the exercises we have done throughout the course. We put them on Post-it notes on a table or wall, then organize them into four categories.

## Sorting features into four MoSCoW categories

Anchor: 1490 · U5 · L20 · 00:40–01:57

The first category is Must-have (captions: *Mass Hub*). These are the basic functionalities the first version of the product needs in order to work. Without them, our product could not function or would not be attractive to users. They are critical at the start of the project; we cannot launch without them. Of course, they are non-negotiable: they have to be included.

Next are the Should-haves. They are important for success, but they do not have to be in the first version. They should, however, be included as soon as possible.

The next category is Could-have (captions: *Cool Hub*). We include these functionalities depending on the time and resources available. They increase customer satisfaction at a low cost, and the product still works without them.

Finally, the Won't-have category (captions: *One Hub*) contains functionalities that are not worth implementing right now. They are often utopian wishes that never get carried out. We put here many functionalities we would like to have, but that are not worth including in our product at this point.

As you can see, this small tool helps us prioritize and negotiate which functionalities to include in our service, product, or application.

## Scoring features in the Functionality Matrix

Anchor: 1490 · U5 · L20 · 01:57–03:01

The Functionality Matrix (*matriz de funcionalidad*) is an Excel sheet in which we add each functionality in a row, based on users. Here we would have different user personas (*personas de usuario*; captions: *distintos y ser persona*) and one row for general functionalities that work for everyone. We write down each functionality we identified in our research and evaluate it using three factors.

The first factor is value for the user. We score it from zero to two: zero means it provides no benefit to the user, one means it provides some value, and two means it provides a lot of value. That goes in the first quadrant. In the second, we enter the benefit for the business: zero means it provides no value to the business, one means it provides some value, and two means it provides a lot of value to the company or business.

Finally, in the third quadrant we enter the task's complexity. Zero means the task is trivial to develop and easy to do. One means it is somewhat difficult or costly. Two means it is very difficult, for example, an advanced search engine.

## Interpreting the colors and negotiating priorities

Anchor: 1490 · U5 · L20 · 03:01–03:59

When we complete these three cells, a score and a color are generated automatically. If the result is green, we have to include it. If it is yellow, we should include it after we finish the basic functionalities. If it is orange, we could include it; if we have time and room left, we will add those functionalities. If it is red, we will discard it from our product.

In the resources section, I am sharing this template so you can apply the Functionality Matrix to your project's functionalities. I want to tell you that the results of both the Functionality Matrix and the MoSCoW method are indicative and negotiable. A red result in Excel does not mean it has to stay out; we can always negotiate it.

Now that we have learned to prioritize functionalities based on their benefit to the user and the company, in the next lesson we will learn what information architecture (*arquitectura de la información*) is.
