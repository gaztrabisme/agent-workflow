## Write user stories around a persona, feature, and goal

Anchor: 1490 · U5 · L19 · 00:00–01:27

In this lesson we will apply user-centered design with two combined tools: user stories (*historias de usuario*) and Jobs To Be Done (*trabajos por realizar*). User stories are very short, schematic descriptions that summarize a specific need a user has when using a product or service, along with the solution that meets it. They are a basic formula that helps us define functions while thinking about the user's need and what they will get from a function. The formula includes a user persona (*persona de usuario*): “As [persona], I want [function] to achieve [goal].”

For example: “As Luis, an older student, I want a book recommender based on affinity so I can discover new books to read.” The Spanish captions spell Luis's playful description as “viejunial.” Another story uses Fede, a UX designer who is “always up to date”: “I want to see the highlights in my UX books so I can remember more and learn from what I read.” Finally, we can use our favourite persona, Mila, a super-reader in her free time: “I want to rate a book so I can recommend books to other people.” This is user-centered design, and it is used a great deal in agile methods such as Scrum.

## Describe the situation and result in a Job Story

Anchor: 1490 · U5 · L19 · 01:27–02:18

Job Stories (*historias de trabajo*) are similar descriptions to user stories, but they use the Jobs To Be Done framework and focus more on the user's situation and the results they will get from using the product. Their formula is: “When I am in [situation], I want [function] so I can achieve [goal].”

## Compare the two forms and combine them

Anchor: 1490 · U5 · L19 · 02:18–02:55

The formulas are very similar, and each has advantages and disadvantages. A Job Story places the user's situation or motivation in the foreground, and its result is more emotional and tied to the experience. A classic user story puts the user, rather than our user persona, at the centre and is more concerned with defining an objective result. The Spanish captions garble this phrase as “nuestro yo soy persona.”

At Elastic Heads, we combine them. The result is: “As Mila, a super-reader in her free time, when she has finished a book, I want to leave ratings so I can recommend books to others and gain recognition.” This formula brings together the best of Job Stories and user stories.

## Use stories to keep the team focused on user value

Anchor: 1490 · U5 · L19 · 02:55–03:32

These stories encourage the team to take part in decisions. We can hold a session and write user stories or Job Stories together. They are created and evolve as the project moves forward and as we learn about users. They are small, concrete requests. Instead of having a stakeholder ask for many functions, we design only what users need. Stories also contain the essential information we need in order to work, support cooperation and collaboration across the team, and, most importantly, make us include only functions that truly add value to the user.

## Add context to make the need clearer

Anchor: 1490 · U5 · L19 · 03:32–04:20

Adding more context to the situation makes it easier to imagine a better solution. For example, needing to eat is different from being in a hurry and needing to eat. It is also different from being in a hurry, hungry, and needing to eat; then we still do not know what I need. It is different again when I am in a hurry, hungry, and have to eat with one hand while walking down the street or riding the subway. If we add still more context, it is not the same as being in a hurry, hungry, having to eat with one hand while out on the street, and not knowing when I will be able to eat again. What do you think I want to eat? Pizza.

With this slightly silly example, you can see that the more context we add about the user's situation, the more it helps us define what they need.
