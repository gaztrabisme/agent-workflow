## What a user flow represents

Anchor: 1490 · U6 · L23 · 00:00–01:12

In this lesson we’ll learn what user flows (*flujos de usuario*) are for and how to make them quickly and effectively. A user flow is a visual representation of the route a user takes to complete a specific task in an app or website. It helps us study how many steps the user has to take and adjust them to meet users’ needs and improve the experience.

Here is an old example of how user flows used to be made. It shows what can happen from the moment a user enters an app and the different paths they can take. For example, what happens if there is an error while logging in, and what happens if login succeeds and takes the user to the home page. Users can take different actions and choose different paths. In the past, different shapes were used for different kinds of decisions.

We need to take users from their entry point through a set of steps to a successful result and a final action, such as buying a product.

## Give each page a purpose

Anchor: 1490 · U6 · L23 · 01:12–02:01

Every page on a website or app needs a purpose. Users need to know what the page is for. On a product page, they should be able to buy the product. On a search page, they should be able to find what they are looking for.

Defining flows helps answer questions such as: How does a user get to a page? Do they navigate from the home page, or arrive through an Instagram campaign? How many steps are in the purchase process? This is especially important for e-commerce and online shops. What can a user do if they land on a particular page? What is the page’s goal? What features will the site have, and which pages will contain them? What do we want the user to do on the site?

In the end, this tool helps us define the experience from a high-level view: the steps and the different options a user can take.

## A quick paper method and a to-do example

Anchor: 1490 · U6 · L23 · 02:01–02:52

There are different kinds of user flow. At Elastic Heads, we make them by hand, using text and a simple formula. At the top, write what the user sees on the current screen; underneath, write what the user does. The next step is what the user sees next, followed by what they do next.

Let’s use an example. Imagine a to-do list app. As users, we tap “Add a new task.” Next we see a form for adding a task. We enter the task description and press “Done” in the upper-right corner. We return to the list, now with the item added. This is a very quick way to define flows in an app or website.

## Mapping login and recovery paths

Anchor: 1490 · U6 · L23 · 02:52–04:20

Let’s look at a login flow. At the top we write what the user sees: the login screen. Underneath, we list the actions they can take. First, they can enter the correct username and password, which takes them into the app, perhaps to a dashboard. Second, they can enter an incorrect password or username, which takes them back to the login page with an error message.

Another option is to click “Forgot password” (captions: *no olvidar la contraseña*). This takes the user to a password recovery screen. There they can enter their email address, which is matched against the username to check whether the account exists. After they submit the email, they return to the login page with a message saying that an email has been sent with a link to recover their password. They open that email, follow its link to reset the password, and see the password reset screen. We have mapped the whole login process quickly and easily.

We can also make flows digitally. We can move the text and arrows, work faster, and duplicate parts, so the process is more efficient. You can use any design program. We could also use sticky notes. As always, I recommend doing this with programmers and stakeholders (*partes interesadas*) so we can find the best options for our flow. Sticky notes can be moved around on a board.

## A complex consumer-loan flow

Anchor: 1490 · U6 · L23 · 04:20–05:14

Here is a hand-drawn example we made for a consumer-loan app. The flow is very complex because we had to validate whether the identification documents were correct, whether the person requesting a loan had debts, and so on. There were many checks—about seven or eight—and it was a complicated process the user would not see. We had to make the experience very simple and easy.

Here we can see how the process moves from screen to screen with different validations. For example, if a user is in arrears and owes money to a bank, we take them to this “No” outcome. If there are no debts or other problems, they continue to the next screen. We worked through this exercise over the course of a day at the client’s offices. It helped us identify how many screens we needed to make and helped the programmers identify the processes they needed to build.

## Choosing a format people can revise

Anchor: 1490 · U6 · L23 · 05:14–06:28

Here is another example: a fairly complex user flow for an online shop’s shopping cart. This one was made in Adobe Illustrator. Personally, I do not like it. It works as a deliverable, but it takes a lot of work and only the person who made it understands it. Do not make flows this complicated and costly. Each time someone asks for a change, we have to edit the file and export it to PDF.

We can also do these exercises in programs such as Miro or Mural (captions: *Mura*). These programs are designed for Design Thinking, but we can still make flows in them. My partner Samuel Hermoso recommended this; he has used it on a project. These tools are quick and work well for iterating with stakeholders.

This other example has a lot of detail in every step, with designed information and a designed flow. That work will not really be valued, because what we want to identify are the steps users need to take to complete a task. It looks good as a deliverable, but, like the previous example, we cannot change anything. It is not editable. I would never recommend making a flow at this level of detail.

## Practical advice for creating a flow

Anchor: 1490 · U6 · L23 · 06:28–07:19

When making user flows for websites, it is important to list the different entry points (*puntos de entrada*): social media, a blog, Google, and so on. We also need to account for both user and business objectives: what the user needs to do in our app. We can make separate flows for different actions. We should consider possible landing pages (*páginas de aterrizaje*) that then lead to a product page (captions: *página de producción*).

Always start with the happy path (captions: *happy pad*): the minimum steps the user needs to achieve their goal. Then add branches until you have the full flow. I recommend making user flows for the different user personas (*user persona*) we have designed. Include only the key screens and add notes to clarify them.

## How user journeys differ from user flows

Anchor: 1490 · U6 · L23 · 07:19–08:22

You may be a little confused about user journeys and user flows, so let’s look at the differences. A user journey, or the proto-journey we made, maps the different steps a user takes to achieve something and shows how the user feels. It helps us identify critical points and develop solutions and many features that can help define the product.

User flows, on the other hand, are deliverables that show the path users take to complete a task. They have an order, but they do not have to be linear; there can be different paths. They do not focus on users’ feelings. If a project is starting from scratch, it is preferable to make the journeys before the flows to discover ideas for new features.
