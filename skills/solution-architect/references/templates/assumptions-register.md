# Assumptions Register — template

*Every unconfirmed thing the solution depends on. On an RFI/RFP where clarification answers may not arrive before the deadline, this is what lets you proceed without fabricating certainty — and protects you when an unanswered question turns out the other way. It is a **primary artifact**: the engagement is not done until this exists and reflects every open item.*

**Rule:** every load-bearing clarification question gets a **paired fallback assumption** here — so that if it goes unanswered you have already stated how you proceed. Pairing is structural, not aspirational: the clarification-questions template carries a "our working assumption" column that maps 1:1 into this register.

**Not the same as the client-obligation register.** An *assumption* is something you believe and can proceed on; an *obligation* is something the client must physically deliver or you stop. If the row would halt the schedule when unmet, it belongs in `client-obligations-register.md`, with a deadline and a named client focal point.

**Surface the high-impact / low-confidence rows in the response itself** (an assumptions annex), framed so the client can correct them. Hidden assumptions become disputes; stated ones become a defensible position.
