# scene-engine SPEC: objection register from a coding agent

Reader: the author of `scene-engine/SPEC.md`.

Perspective: a coding agent given a storyboard and asked to produce an MP4 explainer and an editable deck with scene-engine. The storyboard has scenes with narration text, a chart built from a CSV file, two screenshots of a web app, and a closing title. The agent has read only `SPEC.md` and `README.md`. Question: can the agent drive the tool from that storyboard without guessing?

Severity: **blocking** means the agent would have to guess, the spec contradicts itself, or a builder could not implement the text as written. **non-blocking** means a gap that costs time but does not force a guess. Rows are ranked by impact on this storyboard.

| # | Objection | Spec section | Severity | Why it matters | What would answer it |
|---|---|---|---|---|---|
| 1 | Times use more than one frame of reference, and the spec does not say which applies to most fields. §4 states that layer times are scene-local ("A layer's `startMs` and `durationMs` are local to its scene") and that keyframes are layer-local. It is silent on caption `startMs/endMs`, `narration.audioOffsetMs`, `pptxAtMs`, app-demo `steps[].atMs`, `cursor[].atMs`, `highlights[].startMs` and `check --at`. §5.3 says "Caption cues live on the scene timeline", while §5.1 says the compiler assigns every caption cue "a time relative to storyboard zero". §4 says "app steps and overlay times lie within the app layer", which hints at layer-local time without stating it. | §4, §5.1, §5.3, §6 `check` | blocking | Every caption, narration offset and app click in the storyboard falls in the wrong place unless the agent guesses which origin each field uses. The phrases "scene timeline" and "storyboard zero" pull in opposite directions. | A table that gives the time origin (storyboard, scene, layer or keyframe) for every time-valued field and CLI flag, plus one worked example that converts a caption and an app step to absolute frame numbers. |
| 2 | The spec does not say how narration determines timing. Scene `startMs`/`durationMs` are required and hand-authored. Nothing derives a scene's length from its audio or word timings, and nothing says what happens when the audio is longer than its scene or the storyboard (truncate, error, or overlap into the next scene). §5.3 says cues "may be generated from supplied word timings or authored directly" but gives no flag or field to request generation, and no rules for grouping words into cues. Word-timing `startMs` has no stated origin (audio start, or audio start plus `audioOffsetMs`). | §4 `narration`, §5.3 | blocking | The storyboard is narration-led. The agent cannot size scenes from the voice-over or get captions generated from it without inventing rules the engine may not share. | One of two answers. (a) The engine derives scene duration from audio length plus padding, and names the field that sets the padding. (b) The spec says scenes are authored and defines what happens on overflow: an error code, or truncation. Add a `captions: "fromWordTimings"` switch or equivalent, the rules for splitting words into cues, and the time origin of word timings. |
| 3 | The default renderer is stated two ways. The `render` row says "`auto` is the default: use HyperFrames when installed, otherwise use the fallback". The options table says `--renderer` is "`hyperframes` or `fallback`", default `hyperframes`, and does not list `auto`. | §6 command table vs render options table | blocking | Without a flag, a missing HyperFrames either falls back and exits 0 or fails and exits 3 (`HYPERFRAMES_MISSING`). The two readings give opposite behaviour. | One default stated in both places, with `auto` listed in the options table. |
| 4 | Errors have no catalogue of codes and no field that says how to fix them. Only `HYPERFRAMES_MISSING`, `APP_LOAD_FAILED` and `UNSEEKABLE` are named. The spec gives no code and no exit-code mapping for: a HyperFrames lint failure ("a lint or render failure is reported", which could be exit 1 or 3), an FFmpeg profile mismatch, a step whose locator is never found, an asset that is missing at render time versus at validate time, a caption lint violation, or a `--timeout` expiry during rendering. The validation output gives `"errors":[]` but not the shape of each item; "pointer-coded errors" names no fields. The error example `{"error":{"code","message"}}` has no pointer, layer id, frame or hint field. | §6 exit codes, §4 last paragraph, §5.1, §5.5 | blocking | The agent branches on the code and needs to know which field or file to change. Free-text messages force it to scrape prose. A lint failure could map to exit 1 or exit 3. | A table of error codes with columns: code, exit code, trigger and payload fields (`pointer`, `sceneId`, `layerId`, `frame`, `path`, `hint`). Define the shape of a validation error item, for example `{"pointer","code","message"}`. |
| 5 | App-demo step behaviour is not defined. (a) The schema does not say which fields each action needs: `goto` without `url`, `fill` without `value`, `press` without `key`, and `click` without `locator` all validate. (b) The spec does not say what happens when a step's locator is never found. It covers only the ready selector ("missing readiness selector fails capture", AT16), and gives no per-step timeout. (c) For role plus `name` it does not say whether the match is exact or a substring. (d) It does not give the syntax of fixture `urlPattern` (glob, regex or Playwright URL pattern). (e) It does not say whether requests that match no fixture are blocked, passed through, or raised as an error; "depends on live external state is a capture error" implies detection but gives no mechanism. (f) It does not say whether `cursor` x/y are in stage pixels, layer-box pixels or app-viewport pixels. (g) It gives no browser viewport size. 3840×2160 at scale 2 implies 1920×1080 CSS pixels, but a layer can be any size. | §4 `appDemoLayer`, §5.5 | blocking | If the agent later swaps the two screenshots for a live capture, each of these points either breaks the capture or puts the cursor in the wrong place, with no known error code. | Per-action required fields, written into the schema as `if/then` rules. A `STEP_LOCATOR_NOT_FOUND` code with its exit code, plus a per-step `timeoutMs`. The locator matching rules. The fixture pattern syntax and the policy for requests that match no fixture. The coordinate space for cursor positions. The rule that sets viewport size from the layer size. |
| 6 | Keyframe meaning is incomplete. The spec does not say whether `values` are absolute stage values or offsets from the layer's base properties. It does not say what applies between the layer's start and a first keyframe with `atMs > 0`: the base properties, or the first keyframe held back to the start. It does not say whether the last keyframe holds until the layer ends. It does not give the transform origin for `rotation`/`scaleX`/`scaleY`, or the unit of `rotation` (degrees or radians). | §4 `keyframe`, §5.1 | blocking | Fades and slide-ins for the title and chart come out differently depending on the guess, and the HyperFrames and fallback renderers could disagree. | One paragraph on interpolation that answers each point, with an example: a layer at x=100 that has a keyframe at 500 ms setting x=300. |
| 7 | Defaults are missing for fields the storyboard needs. Text `style` has no defaults for `fontFamily`, `fontSize`, `color`, `align` or `lineHeight`. The spec does not say how text wraps or overflows its box, or whether it auto-fits. §5.4 promises "bullets" in PPTX output, but the text layer has no field for bullets. Scene `background` has no default. Image `fit` has no default. The chart has no colours, axis titles, number format or font. The spec does not say what is rendered in the gaps when scenes do not cover all of `durationMs`. | §4 `textLayer`, `imageLayer`, `chartLayer`, `scene` | blocking | The closing title and chart look different between video and PPTX, or between builds, unless the defaults are fixed. Unknown properties are rejected, so the agent cannot add its own styling fields. | A `default` on every optional field. A text overflow rule (clip, shrink or error). A bullets field or a markup convention for bullets. A gap rule (background colour or black). Chart styling fields, or a stated house style. |
| 8 | "Project directory" is undefined. The spec says "All asset paths are relative to the storyboard file and must resolve inside its project directory". It does not say whether the project directory is the storyboard's own directory, the nearest ancestor containing a marker file, or a flag. It does not say whether symlinks are followed, whether `fixtures[].bodyFile`, `narration.wordTimings` and `video.poster` follow the same rule, or whether the output paths `--out`/`--out-dir` may lie outside it. | §4 opening paragraph, §6 options table, AT02 | blocking | The screenshots and CSV-derived assets may sit in a sibling folder. Whether they pass depends on a definition the spec does not give, and AT02 tests exactly this rule. | A definition of the project root, for example "the storyboard's directory unless `--root` is given", with the symlink policy and the list of fields this rule covers. |
| 9 | Command output JSON is described but not specified. `render` output "includes files, duration, frame count, media streams, renderer/version and diagnostics", with no field names. `export-pptx`, `capture` and `check` outputs are described the same way. Only `validate` and `selftest` show their shape. The spec does not say whether a failed profile probe deletes or keeps the MP4; only AT06 says "no MP4 is published", and that is for seek errors. | §6 command table | blocking | Checking the result means reading these documents. Without field names the agent has to inspect sample output first, and none exists. | One JSON Schema per command output, including the per-slide native/raster mapping and the nested `rk` report. A rule for whether partial outputs are kept on exit 1. |
| 10 | `capture --scene <id>` cannot select one layer from a scene that has several app-demo layers. The spec does not say whether `render` reuses frames from an earlier `capture --out-dir` or always captures again. No flag points `render` at captured frames. | §6 `capture`, `render` | blocking | Whether one or many layers are captured is a guess. Capturing again on every render slows iteration, and a cache could be keyed wrongly. | A `--layer <id>` option, and a rule on whether render reuses frames, keyed by content hash, or a `--frames-dir` flag. |
| 11 | No command renders one scene or a time range. `render` has no `--scene`, `--from/--to` or `--frames` option. `check` captures still frames only. The only way to see motion is a full render that captures every app-demo layer and runs two-pass loudnorm. | §6 | non-blocking | Iterating on one scene's timing costs a full render each time. | `render --scene <id>` or `--range <startMs>-<endMs>`, plus a `--draft` mode that skips normalization and loudnorm. |
| 12 | `--strict` is described for `check` ("`--strict` turns skipped into exit 1") but is missing from the `check` synopsis. The options table says it is "on in CI" but does not say how CI is detected. `check` with no `--rk` defaults to a "configured sibling checkout", with no stated configuration key or environment variable. | §6 `check`, options table | non-blocking | The agent cannot tell whether a skipped `rk` run counts as a pass on this machine. | Add `--strict` to the synopsis. Name the CI signal (for example `CI=true`). Name the configuration source for the `rk` path. |
| 13 | Charts take only inline `categories`/`series`. The spec has no CSV source, no rule for converting or rounding numbers, and no description of how the HTML chart is drawn for video or animated in. It mentions only `data-rk-chart` markup for checks. The spec allows `stacked` and `combo` but does not say which series `kind` values and axes `stacked` permits. | §4 `chartLayer`, §7 | non-blocking | The agent can turn the CSV into inline arrays itself. Without the drawing rules it cannot predict how the video chart will look next to the native PPTX chart. | Either a `dataFile` CSV field with column mapping, or a statement that inline data only is by design. One paragraph on how charts are drawn and animated in HTML, and the constraints on series for `stacked` and `combo`. |
| 14 | No example storyboard is given. The acceptance tests cite `fixtures/at01/…` to `fixtures/at19/…`, but neither the spec nor the README includes or points to them. The spec has no complete storyboard with narration, captions, a chart, an image and a closing title, and no example word-timings file used to create captions. | §4, §8, README | non-blocking | A cold agent has to assemble its first storyboard from the schema alone and find the semantic errors one validate run at a time. | One complete annotated example storyboard in the spec, and the fixture paths stated relative to the repository. |
